# Execution Brief

## Why

- Harness configuration is currently file-only: `harnesses.json` exists (seeded by workspace v2 bootstrap) and the registry already merges it over built-ins with last-write-wins shadowing, but nothing in the product lets a user *operate* that mechanism. This step gives it a surface.
- The binary-path override is the remedy for STEP-25-01's detection states: `not-installed`/`probe-failed` frequently mean "installed somewhere PATH doesn't reach" (notably: macOS GUI-launched Electron lacks the login-shell PATH). Detection guidance without an override field would be a dead end.
- Per-project default harness is what makes the two-harness reality usable day-to-day: PHASE-24 gave `SProject.defaultHarnessId` storage and the `project:set-defaults` IPC; this step gives it an editing surface so "this repo uses opencode, that one uses Pi" sticks.

## Prerequisites

- STEP-25-01 merged (`detectHarness`, `detectCommand` field, opencode definition — the list this UI renders).
- STEP-24-02 merged (ProjectStore, `project:set-defaults` IPC, per-project `defaultHarnessId`).
- Read: `packages/harness/src/registry/registry.ts` (merge precedence — a workspace entry sharing an id **replaces the built-in wholesale**; this drives the override design below), `packages/contracts/src/workspace/layout.ts` (`workspaceFiles.harnesses`, seeded `{"version":1,"harnesses":[]}`), `packages/desktop/src/main/services/settings.ts` + `workspace.ts` (`registerSettingsHandlers` pattern; `afterRootChanged` re-root hook), `packages/desktop/src/renderer/components/Settings.tsx` (`SettingsPanel`/`SettingsSection` model — sections render as one scrollable column).

## Likely Code Paths

- `packages/contracts/src/ipc/contracts.ts` — new channels following the settings pattern (`parseSync` at the boundary):
  - `harness:list` → response carries a **top-level `workspaceLoad` result** (`ok`, or the typed `loadWorkspaceHarnesses` failure with its readable message) *distinct from* the per-harness rows — an invalid `harnesses.json` must be distinguishable from a valid workspace with no custom entries, and the section-header error surface (constraint below) renders from exactly this field. Then per harness: merged definition, `source`, whether a workspace override shadows a built-in, and `DetectionResult`. **Capabilities do NOT ride on this channel** — STEP-25-03 reads them from its own `harness:capabilities` channel (decided there); `harness:list` stays the configuration/detection view so the two payloads never drift into two competing capability shapes.
  - `harness:save-override` and `harness:reset-override` (id) → mutate `harnesses.json`. **`harness:save-override` takes a COMPLETE `SHarnessDefinition`, never a patch** — the schema at the `parseSync` boundary rejects a partial record, and the renderer builds its payload by editing the full definition object `harness:list` returned for that id. Because the registry replaces wholesale, a payload missing `capabilityOverrides`, `quirks`, `detectCommand`, or `source` is not "unchanged" — it is a deletion of those fields, silently changing detection and capability safety (e.g. dropping Pi's `mcpServers` clamp). If the executor prefers a patch-shaped channel instead, then the service MUST perform an explicit field-level merge over the current effective definition before writing, and the same regression test applies; the recorded default is full-definition round-trip because it needs no merge code.
    - **Completeness is not integrity — the payload is untrusted input, not the record.** A *complete* `SHarnessDefinition` still decodes fine when the renderer (or any scripted IPC caller) flips `quirks`, `capabilityOverrides`, `source`, or the identity fields — a caller could clear Pi's `mcpServers` clamp or its `adapter-mediated` quirk and the schema would happily accept it. So the service **canonicalizes every save against a base record instead of storing what it was handed**: the base is the built-in definition for a built-in-shadowing id, or the entry currently in `harnesses.json` for a custom id. Only an explicit **allowlist** of fields may come from the payload — `launch.command`, `launch.args`, `launch.cwd`, `launch.env`, and `detectCommand` (exactly what this step's editor exposes). Everything else — `id`, `name`, `description`, `source`, `quirks`, `capabilityOverrides`, `docsUrl` — is re-derived from the base and any differing payload value is **ignored, not written**. Two cases are hard errors rather than silent normalization, because they mean the caller is confused about *which* record it is editing: a payload `id` that does not match the channel's target id, and a payload claiming `source: 'builtin'` for an id with no built-in behind it. This is a service-level rule, not a renderer rule — the renderer's full-definition round-trip stays the happy path and produces a byte-identical canonicalization, but nothing downstream may depend on the renderer behaving.
- `packages/desktop/src/main/services/harnesses.ts` (NEW service, `services/` module pattern): builds the registry from built-ins + `loadWorkspaceHarnesses(harnesses.json)`, runs `detectHarness` per definition (results cached per app run; re-probe on demand via a refresh param), writes `harnesses.json` atomically (tmp+rename) **and serialized**: saves flow through a per-workspace write queue in the main service, and each queued save re-reads the current file before applying its mutation — atomic rename alone lets two settings surfaces read the same old state and silently drop each other's entries on the last rename. **The built-ins fallback is a LISTING affordance only — it must never authorize a write.** `loadWorkspaceHarnesses` returning its typed failure means "the file exists and we could not understand it", which is emphatically not "the workspace has no custom harnesses": if save/reset treat that failure as an empty workspace, the re-read-then-mutate step rewrites the file from thin air and a malformed — or merely concurrently hand-edited — `harnesses.json` is silently overwritten, destroying every custom entry in it. So the re-read inside `harness:save-override` / `harness:reset-override` **aborts on a load failure**: the typed error is returned to the caller (the same readable message `harness:list` surfaces), no tmp file is created, and the existing file is left byte-for-byte untouched until the user repairs it. Only a *successful* load — including the legitimately empty `{"version":1,"harnesses":[]}` — permits a mutation. A missing file is not a load failure: it decodes as the empty workspace and may be created. Re-roots via `WorkspaceService` hooks exactly like semantic-search. `@srgnt/harness` import uses the lazy-ESM pattern (CJS main).
- **Override semantics (grounded + Decision needed, default recorded):** the registry's shadowing is wholesale-replace, so "override binary path/env" = write a *full copy* of the built-in definition with edited `launch.command`/`launch.env`/`detectCommand` into `harnesses.json`; "Reset to built-in" = delete that entry. Default: keep wholesale-shadow (zero new merge code; matches shipped registry semantics). Consequence to surface honestly: a shadowed Pi will NOT pick up future built-in changes (e.g. a `PI_ACP_VERSION` bump) until reset — the UI must show an "overridden" badge on shadowed built-ins. Alternative (delta-patch overrides merged at load) rejected for now; note it for Phase 26 if the lessons-learned demands it.
- Renderer — new Harnesses section in Settings (either a `SettingsSection` with custom rows or a dedicated `components/settings/HarnessSettings.tsx` rendered alongside `SettingsPanel`; follow whatever composition Phase-23/24 left in the settings route). Per-harness card: name, source (builtin/custom), detection status chip rendering all three `DetectionResult` states (`ok` + version / `probe-failed` + reason / `not-installed` + install hint from description + `docsUrl` link), binary path (`launch.command`) input, **detect command (`detectCommand`) input** (optional; placeholder shows the default = launch command), env var key/value editor, overridden badge + Reset. `detectCommand` must be editable here, not just the launch fields: the full-copied Pi definition retains `detectCommand: 'pi'`, so a user fixing the GUI PATH problem by pointing `launch.command` at an explicit path would spawn sessions fine while `detectHarness` keeps probing bare `pi` and the card stays `not-installed` — the editor has to let them update or clear `detectCommand` so detection follows the fix. Semantic tokens only.
- Per-project default harness: a "Default harness for <active project>" selector in the same section, listing registry ids and writing through the existing `project:set-defaults` IPC. (**Recorded assumption:** it lives in Settings next to the harness list; the ProjectSwitcher side panel may mirror it later — don't build both now.) **Dangling default is a defined outcome, not a fallback hand-wave:** the stored `defaultHarnessId` can point at an entry that was reset or deleted, so session creation resolves it through `require(id)` inside a typed catch — when it fails and the caller supplied no explicit harness, creation **blocks** with an actionable error naming the missing id; the renderer surfaces the harness picker and writes the choice back as the new project default. No deterministic built-in substitution (spawning a harness the user did not choose is dishonest), no silent no-op, no unhandled `UnknownHarness`.
- **Env editor — secrets are designed out, not warned about.** `harnesses.json` sits in the workspace, so anything stored there travels through source control, backups, and shared filesystems; a warning label does not stop that, and a token pasted once is leaked permanently. The mechanism, decided here so it exists before implementation:
  1. **Reference, don't copy.** A value may be written as a reference `${env:NAME}` (and only that form), resolved at spawn time from the main process's own environment and never persisted. This is the supported way to give a harness a token, and it is what the placeholder/help text teaches.
  2. **Reject sensitive literals at the service, not in the UI.** A save whose *literal* value lands on a key matching the sensitive-key pattern (case-insensitive `TOKEN|SECRET|KEY|PASSWORD|PASSWD|CREDENTIAL|AUTH|COOKIE|SESSION`) is refused by `harness:save-override` with an actionable error naming the key and offering the `${env:…}` form — enforced at the boundary so a bypassed renderer, a scripted IPC caller, or a future second surface cannot store it either. (Hand-edited `harnesses.json` is out of the product's reach; the linter-style warning on load is fine for that case, but the product never *writes* one.)
  3. **Least privilege on the file that remains.** `harnesses.json` is written `0600` (owner-only) by the same atomic tmp+rename path — the tmp file is created with the same mode, so the secret-free-but-still-private config never passes through a world-readable state.
  Preferred v1 = reference + rejection + `0600`; OS-keychain-backed storage is the acknowledged stronger option and is deliberately deferred (it needs a credential-service surface this phase does not have) — record it as a Phase-26 candidate rather than half-building it. The renderer only ever sees what the user typed — never `process.env` (so it cannot enumerate the values a reference resolves to).

## Key Design Constraints

- Settings take effect **on next spawn**: the supervisor's handles are lazy per session — saving an override rebuilds the registry so new sessions launch with the new spec; already-running processes are deliberately untouched (no kill/respawn in this step; document that in the UI copy "applies to new sessions").
- **Per-harness permission policy defaults (phase scope line) — Decision needed, default recorded: DEFER.** No contract field exists for it; per-project `permissionPolicy` (STEP-24-02) remains the only relaxation surface this phase. If the human wants it now, the minimal shape is an optional `harnessDefaults` record on `SDesktopSettings` — but default is to leave it to Phase 26 with the lessons-learned as input.
- `harnesses.json` is user-editable by hand: the service must survive concurrent/external edits (reload on read; schema-invalid file → readable error + built-ins fallback, which `loadWorkspaceHarnesses` already returns as a typed failure — surface it in the section header, do not silently swallow). **That fallback covers reads only:** `harness:list` renders built-ins plus the error, while save/reset refuse to run against an unreadable file and return the load error instead (see the service bullet) — the product never repairs a broken `harnesses.json` by overwriting it, because the file it cannot parse is still the user's data.
- Custom (non-builtin) entries in `harnesses.json` must render and be editable too — but *creating* new custom harnesses is Phase 26 (editor); this UI edits/deletes what exists, no "Add harness" button.
- Default-ask permission stance untouched; nothing in this UI relaxes permissions.

## Execution Checklist

1. IPC contracts + preload surface (+ contracts tests).
2. `services/harnesses.ts`: registry build, per-definition detection, atomic `0600` save/reset with full-definition round-trip, base-canonicalized field allowlist, load-failure abort on mutation, and sensitive-key rejection + `${env:…}` resolution at spawn, re-root hook; unit tests with injected probes and a temp workspace. Two of these are **direct service/IPC-boundary tests, never routed through the renderer**: (a) a COMPLETE but tampered `SHarnessDefinition` (valid schema, but with `quirks` emptied, `capabilityOverrides.mcpServers` flipped to `true`, and `source` switched) → the stored record keeps the base's values for all three and the tampering is not written, while a payload whose `id` does not match the target is rejected outright; (b) save and reset against a workspace whose `harnesses.json` fails to load → both return the load error with the file untouched.
3. Renderer harness section: cards, detection chips, override editor, reset, overridden badge; component tests.
4. Per-project default harness selector wired to `project:set-defaults`.
5. Integration test: override `launch.command` to fake binary A, spawn a session (mock-driven), assert the spawned command is A; reset; assert built-in command again.
6. Manual pass: break PATH for opencode → chip shows not-installed + install guidance; set explicit binary path (updating `detectCommand` where the definition carries one, e.g. Pi) → chip flips to ok after re-probe.
