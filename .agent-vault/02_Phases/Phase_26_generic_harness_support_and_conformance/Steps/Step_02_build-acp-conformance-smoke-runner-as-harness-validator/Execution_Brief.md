# Execution Brief

## Why

- A user-provided definition is a claim; the conformance runner turns it into evidence. It is the trust story for arbitrary harnesses: scripted `initialize` → `session/new` → prompt → cancel against a REAL user-configured agent binary, reported per-check as pass / fail / not-supported — plus *suggested quirk flags* the user can apply in the STEP-26-01 editor. This is the "Test this harness" button the capability matrix deliberately did not build (STEP-25-03 recorded assumption: no auto-probe — that button is this step).
- The inversion framing from the phase note is literal: the mock-agent suite scripts the **agent** side against our real client; the conformance runner scripts the **client** side against a real agent. Nearly every piece exists as prior art — the job is composition, not invention:
  - `AcpAgentConnection` (`packages/harness/src/acp/connection.ts`) already exposes exactly the probe surface: `connect` (spawn + initialize + `capabilities`), `newSession`, `loadSession`, `resumeSession`, `prompt`, `cancel`, `close`, with injectable `AgentSpawner` and `ClientPorts` (permission/fs/terminal) for instrumentation.
  - `pi-spike.integration.test.ts` is a hand-rolled one-harness conformance run: probes 1 (permission round-trip), 2 (MCP passthrough via `testing/fixtures/mcp-echo-server.mjs` + `MCP_ECHO_LOG` handshake evidence), 3 (capabilities/load/resume), 4 (fs/terminal delegation), with evidence files. Generalize its probes; keep its evidence discipline.
  - `registry/detect.ts` gives the typed pre-flight (`ok`/`probe-failed`/`not-installed`); the mock agent (`testing/mock-agent/`) is the scriptable agent every unit test runs against; `supervisor/kill-tree.ts` + the `hang-probe.mjs` fixture are the no-orphans prior art.
- **REQ gate RESOLVED 2026-08-15 — *requirements reconciliation only; no code was written or validated.* The lessons note lands twelve requirements here, and they freeze the check catalog** — REQ-26-09 through 15 and 18 are the runner's own; REQ-26-03/04/05 are shared with the editor, and REQ-26-17 is a cross-cutting guard. Read it, then build to these:
  - **REQ-26-09 permissions, REQ-26-10 MCP passthrough, REQ-26-11 fs/terminal delegation, REQ-26-12 load/resume** — all four must be probed **behaviorally**, never read off `initialize`. This is the note's headline: `initialize` advertises dishonestly in both directions. Pi advertises `mcpServers` and never launches the echo server; opencode advertises `loadSession` and `resume` and neither was ever driven. REQ-26-10 names `mcp-echo-server.mjs` for reuse verbatim; REQ-26-11 records that fs/terminal delegation is currently only *declarable* (pi's `no-client-delegation` quirk), so the probe is what turns a declaration into a measurement.
  - **REQ-26-12 additionally requires reporting *advertised* separately from *working*.** One column cannot carry both — pi advertises `resume` and answers `-32601 Method not found`.
  - **REQ-26-13 — at least one prompt turn, with mid-session discoveries folded in one-way.** An `initialize`-only report under-reports the agent: opencode's first turn carries 93 slash commands its `initialize` says nothing about. **Reuse `mergeSessionCapabilities` and `SESSION_DISCOVERED_CAPABILITIES`; do not re-implement the merge.** The note flags that the one-way rule broke three different ways across three consecutive review rounds on PR #32 — treat a re-implementation as a defect waiting to happen.
  - **REQ-26-14 — carry the agent's raw claims beside the normalized row**, at minimum `sessionCapabilities` and `mcpCapabilities`, including keys srgnt does not model (`close`, `fork`). `not measured` must be a distinct state from `no`. This is also what makes the report useful for PROP-B, which needs a behavioral probe before any requirement can be written from it.
  - **REQ-26-15 — auth: classify through the shipped `normalizeAuthMethod`, never construct a login command from prose.** The wall is JSON-RPC **`-32000`**, verified in `@agentclientprotocol/sdk` 1.2.1 source; `Effect.runPromise` drops the code, so capture it with `Effect.tapError` (this is shipped knowledge from STEP-25-03 — reuse the detection, do not rediscover it).
  - **REQ-26-18 — report `configOptions` and flag them as unreachable.** Both harnesses return them and srgnt drives none of them. **Scope DECIDED 2026-08-15: report only — the driving surface is [[04_Decisions/DEC-0021_adopt-acp-session-config-options-and-retire-the-modes-path|DEC-0021]] and belongs to a later phase.**
    **The report must caveat its own blind spot, or it lies.** `session.configOptions.boolean` is a *client* capability, and `buildClientCapabilities` (`packages/harness/src/acp/connection.ts:171`) advertises only `fs` and `terminal` — so an agent may legitimately withhold boolean config options from srgnt. A missing boolean option is therefore **not** evidence the agent lacks one. Say so on the row. Do **not** "fix" this by advertising the capability: this codebase advertises from the implementation's presence (the same file sets `writeTextFile: false` when the port lacks the method, calling the alternative "a capability lie"), and srgnt cannot yet handle what it would be claiming.
    For reference when that later phase runs: `session/set_config_option` is measured working against opencode 1.18.18 with `{sessionId, configId, value}` (addendum in the opencode capture note), and the spec supersedes `modes` with config options.
  - **REQ-26-03/04/05** also touch the runner: a clamp is a visible state, suggested quirks are never auto-applied, and a re-measure must be reachable after an edit.
  - **REQ-26-17 — the runner must be callable from CommonJS desktop-main.** Already this brief's lazy-ESM pattern; the REQ exists because 25-02 hit `ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING` and needed an injectable loader. Keep the loader injectable for tests.

## Likely Code Paths

- `packages/harness/src/conformance/` (NEW module beside `acp`/`registry`/`testing`): `checks.ts` (the catalog), `runner.ts` — pure function: `(definition, options) → ConformanceReport`, injectable spawner/timeouts, **no disk writes and no Electron** (package rule; callers persist/render).
- Report contract: `SConformanceReport` in `packages/contracts/src/` (assumption — it crosses IPC to Settings, so it is an app contract like `SHarnessesFile`): per-check `{ id, title, status, reason?, evidence?, detail? }`, plus negotiated capability row, agent info, suggested quirks, timings, `ranAt` + definition snapshot. **Canonical vocabulary (frozen — the runner, IPC, Settings UI, and every test consume exactly this; the step note and Validation Plan use the same words):** `status` is the ONLY status enum and has exactly four members — `pass | fail | not-supported | skipped`. Everything else the docs mention (`not-installed`, `auth-required`) is **not** a status; it is a structured `reason` code carried alongside a status. Specifically: a not-installed detect result is `status: skipped` with `reason: 'not-installed'`; an unauthenticated harness is `status: skipped` with `reason: 'auth-required'` on the downstream checks (and the auth check itself reports the advertised methods as its evidence); a deep probe the run did not opt into is `status: skipped` with `reason: 'deep-probe-not-run'` (see the deep-probe split below — those checks are always *present* in the report, never omitted). Do not introduce a fifth status or use these reason codes as statuses anywhere.
  **`reason` is single-valued, so its precedence is fixed here (ordered by what the user must fix first):** `not-installed` > `auth-required` > `deep-probe-not-run`. A shallow run against an unauthenticated harness therefore reports checks 8–9 as `auth-required`, not `deep-probe-not-run` — enabling the deep-probe toggle would not have helped, and telling the user to enable it would send them at the wrong problem. Carry the lower-precedence reasons in the check's `detail` so nothing is lost ("also not run: deep probes were disabled"). Never emit two reasons; never let a consumer guess which applied.
  **Report-level coverage fields (`SConformanceReport`, so the shallow-run statement has somewhere to live):** `coverage: { depth: 'shallow' | 'deep', checksSkipped: Array<{ id, reason }>, requirementsNotExercised: string[] }`. `requirementsNotExercised` carries REQ ids (e.g. `REQ-26-09`, `REQ-26-10`) and is **derived from the check results, not maintained by hand** — a check-id→REQ-id map lives beside the catalog so the two cannot drift. This is what the header renders and what the JSON export carries; a consumer must be able to tell a shallow run from a deep one without re-deriving it from per-check reasons.
- Check → ACP method map (v1 catalog; confirm against REQ-26-xx):
  1. **detect** — `detectHarness(definition)` not-installed → this check is `status: skipped, reason: 'not-installed'`. In the **full-report mode** (the "Test this harness" report run) it short-circuits every downstream check to `status: skipped` (never `fail`) — spending spawn attempts on a binary we know is absent buys nothing.
  2. **spawn + initialize** — `AcpAgentConnection.connect` via `childProcessSpawner` → protocol version, `agentInfo`, `negotiateCapabilities` row. **Split the two failures explicitly, because STEP-26-01's test-launch button depends on the distinction:** `reason: 'spawn-failed'` (the process never started — ENOENT, permission denied, immediate non-zero exit; evidence carries the OS error) vs `reason: 'initialize-timeout'` / `'initialize-failed'` (the process started but never answered `initialize`, or answered with an error/protocol violation). "The binary is missing" and "the binary is not an ACP agent" are different user problems with different fixes, and only the spawn attempt can tell them apart.
  - **Two run modes over one engine (the shared test-launch contract, decided):** `mode: 'report'` (the full catalog, detect-first and short-circuiting as above) and `mode: 'launch'` (checks 1–2 only — what STEP-26-01's "Test launch" button calls). In `launch` mode **detection is advisory and never short-circuits**: the runner always attempts the spawn, so the result is always a real launch outcome — a missing binary surfaces as `status: fail, reason: 'spawn-failed'` with the detect result attached as context (`detected: 'not-installed'`), NOT as a `skipped` / `not-installed` result. Both modes return the same per-check shape; only the catalog and the short-circuit rule differ. Nothing downstream may re-derive these outcomes: `not-installed` remains a reason code, `spawn-failed` and `initialize-timeout` are distinct reason codes, and the STEP-26-01 button renders whichever it is told.
  3. **auth advertisement** — `authMethods` from the negotiated row; if `session/new` later fails with the verified auth-required shape, mark the downstream checks `status: skipped, reason: 'auth-required'` (the auth check itself carries the advertised methods as evidence) — an unauthenticated harness is a *finding*, not a runner failure.
  4. **session/new** — sessionId returned; modes advertised (or not).
  5. **prompt turn** — one trivial prompt; assert stream sanity (updates observed, `stopReason: end_turn`); record the update-kind distribution as evidence (the lessons note's stream-shape axis).
  6. **cancel** — second prompt, `session/cancel` mid-turn → expect `stopReason: cancelled` within a timeout (mock `expect_cancel` + spike prior art).
  7. **session/load / resume** — attempt per advertisement, and **report the two methods as two separate check results, each with its own suggestion**: `session/load` failing and `session/resume` failing are different defects with different Phase-24 consequences (load drives resume-by-replay; resume drives transparent continue), so one shared result would file a resume failure under a load quirk. **A quirk describes a harness that misbehaves, never one that simply lacks a feature:** if `loadSession`/`resumeSession` is not advertised, that method's check is `status: not-supported` and suggests NOTHING (an agent without session load is a normal agent, and Phase-24's read-only+fork path already handles it honestly). A quirk is suggested only when the harness **advertises** the capability and the attempted call fails (error, `-32601`, empty/no replay) — advertised-but-broken is the defect the quirk exists to record. **Method-specific codes (decided, and this is the option this step implements):** an advertised-then-failing `loadSession` suggests `no-session-load`; an advertised-then-failing `resumeSession` suggests `no-session-resume`. `SHarnessQuirk` in `packages/contracts/src/harness.ts` currently declares only `no-session-load`, so **this step adds `no-session-resume` to that literal union** (with the doc-comment line beside its siblings: *`session/resume` advertised but unsupported; reconnect falls back to `session/load` replay, then read-only + fork*) — never reuse `no-session-load` for a resume failure, and do not collapse both into a method-neutral code (the STEP-26-01 editor and the Phase-24 cascade both need to know which method to distrust). Same rule for a harness that does not advertise but is attempted opportunistically: a failure there is `not-supported`, not a quirk.
  8. **permission round-trip (behavioral, deep)** — instrumented `PermissionPort` **plus instrumented fs/terminal `ClientPorts`**; a prompt scripted to force a *protected tool action* (e.g. write a file / run a command), not merely a permission-inviting phrasing. The `permission-routing-gaps` suggestion requires **two conditions together**: (a) evidence the agent attempted the **specific protected, client-mediated action the probe scripted** — an observed `fs/write_text_file` (or other write-class `fs/*`) or `terminal/*` call arriving on our instrumented `ClientPorts`, or fixture-grade proof of that same action (the probe's target file created/modified on disk, the probe's marker command having run) — AND (b) zero `session/request_permission` observed for it. **A generic tool-call record in the update stream is NOT sufficient evidence** on its own: an agent may report a tool call that it executed in-process (Pi's adapter does exactly this — spike probe 4, no delegation), or one that is a read, a search, or an entirely unrelated action that srgnt never expected to gate. Counting that as a routing gap would flag a harness for not asking permission for something we never protected. Only a client-mediated protected action — one whose execution *must* pass through our ports — proves the gate was bypassed; use the stream's tool-call record as corroborating detail, never as the trigger. Zero `request_permission` *alone* is likewise not a finding: with a real model the agent may answer in prose or take another path without ever attempting the action, so a run where the protected action was not attempted reports the permission check as `not-supported`/inconclusive (record why, including what the agent did instead), never as a routing gap. This avoids the false-positive the spike's single-probe design risked (spike probe 1).
  9. **MCP passthrough (behavioral, deep)** — inject `mcp-echo-server.mjs` via `session/new` `mcpServers` with `MCP_ECHO_LOG`; handshake lines in the log prove passthrough (spike probe 2, reusable verbatim). **Suggest `mcp-passthrough-gaps` only when the harness advertises an `mcpServers` capability (or accepts the `session/new` `mcpServers` payload without rejecting it) and the handshake never arrives** — that is an accepted-then-dropped promise. A harness that advertises no MCP support reports `status: not-supported` and suggests nothing; a harness that explicitly rejects the payload reports `not-supported` with the rejection as evidence. Labelling ordinary absence of MCP support as a harness defect would put a false quirk on every non-MCP agent.
  10. **teardown** — `close()`; process exits within grace; kill-tree fallback; orphan check.
- **Deep-probe split — RECONCILED 2026-08-16 against the frozen REQs, because as written the two contradicted each other.** Checks 8–9 run real model turns: they cost tokens and need a provider-configured agent, so the default run stays **deterministic checks 1–7, 10**, with a "deep probe" toggle opting into 8–9 behind cost copy. Trivial prompts only (the Phase-25 cost rule). **But checks 8 and 9 are REQ-26-09 and REQ-26-10 — frozen behavioral requirements** — so a default run that simply omitted them would emit a report claiming conformance coverage it never attempted. That is the exact failure this whole phase exists to prevent.
  **The rule, therefore:** a skipped deep probe is *reported*, never *absent*. Checks 8 and 9 always appear in the report; in a default run they carry `status: skipped` with a new reason code **`deep-probe-not-run`** (added to the reason vocabulary beside `not-installed` and `auth-required` — it is a reason, not a fifth status), and the report header renders `coverage.depth` and `coverage.requirementsNotExercised` from the contract fields defined above. A reader must never have to know the toggle's default to know what was measured. When a higher-precedence reason also applies (not-installed, auth-required), that one wins per the ordering above and the deep-probe omission moves to `detail`.
  Corollary for the suggested-quirks list: `permission-routing-gaps` and `mcp-passthrough-gaps` **cannot be suggested from a default run at all**, since neither probe ran. The report must say so rather than presenting an empty quirk list as a clean bill of health.
- Desktop wiring: `harness:conformance-run` IPC in `contracts.ts`; main service invokes the runner (lazy-ESM import) with a hard overall timeout; Settings per-harness card gains "Test this harness"; report rendered per-check with evidence expanders; **JSON export** via Electron save dialog writing the `SConformanceReport`-encoded payload (assumption: file export, not clipboard). **Decision needed (default recorded):** single request/response with an in-flight spinner, no streaming progress channel in v1.
- **Duplicate-run serialization owner (main process, not the renderer):** the main service keeps a per-definition in-flight guard (a map keyed by the definition's id/fingerprint). A second `harness:conformance-run` for a definition already running is rejected (or queued behind the first) at the IPC handler — renderer spinner/debouncing is insufficient because multiple callers or windows can each fire the IPC. The **main service also owns report persistence** (writing/returning the `SConformanceReport`); the runner stays pure (no disk), and the renderer only renders/export-triggers. This is what the Validation Plan's "second concurrent run rejected or queued" check exercises.

## Key Design Constraints

- The runner must never hang: every check has its own timeout; a hung agent gets the kill-tree treatment (test with `registry/__fixtures__/hang-probe.mjs`).
- Suggested quirks are never auto-applied — the report suggests; the user applies via the STEP-26-01 editor. **Decision needed (default recorded):** an "apply suggested quirks" button that *pre-fills* the editor is allowed; silent mutation of `harnesses.json` is not.
- Not spec certification (phase non-goal): checks probe practical capability srgnt actually consumes, nothing more.
- All suites green with no real agent installed: unit tests run the checks against the in-process and stdio mock agent; real-harness runs are env-gated ITs (`SRGNT_IT_PI=1` / `SRGNT_IT_OPENCODE=1` pattern).
- STEP-26-01's "test launch" button delegates to this runner in `mode: 'launch'` (checks 1–2, spawn always attempted) — one probe engine, two entry points, one reason-code vocabulary. If STEP-26-01 shipped its own inline probe first, retarget it onto this engine rather than leaving two definitions of "launch failed" in the product.
